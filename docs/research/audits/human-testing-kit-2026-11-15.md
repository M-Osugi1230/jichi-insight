## §1 実機スマートフォン確認

- **所要時間の目安: 45〜60分**
- **記録先: Issue #12（不具合は個別 Issue を起票してリンク）**
- 前提: 所有者の iPhone を使用。主要導線はスマートフォン前提で設計されている（チェックリストで確認済み）ため、実機での最終確認が対象。

### 手順

1. ブラウザ（通常使うもの）でトップページを開く。キャッシュの影響を避けるため、可能ならプライベートブラウズで開く。
2. 下記「主要導線」を順にたどり、各ページで「チェック観点」を確認する。
3. 気づいた点はその場でスクリーンショットを取り、ページ名と操作をメモする（記録様式に転記）。

### 主要導線

1. トップ → 全国カバレッジ → 自治体ページ（宮城県）
2. トップ → レビュー進捗 → 任意の自治体の「公式資料の索引」リンク
3. 自治体ページ → 出典（公式資料 PDF リンク）→ ブラウザバックで戻る
4. トップ → データ品質 → 訂正・反論 → 変更履歴
5. フッターの各リンク（利用規約、プライバシー、免責、ライセンス）

### チェック観点

- [ ] 横スクロールが発生しない（表・カード・長い数値を含むページで特に確認）
- [ ] 文字が小さすぎて読めない箇所がないか（静的所見: 約8〜10px の注記が多数。出典フッタ、タイムラインの値などを実物で判定する）
- [ ] タップ対象（リンク、チップ切替、details の開閉）が指で押し間違えずに操作できる
- [ ] チップ切替（宮城県ページ等）の選択状態が色以外でも判別できる
- [ ] 状態ラベル（Reviewed / Partial / Not linked 等）が色だけに依存せず読める
- [ ] 外部リンク（公式資料 PDF）が開き、形式・ページ数の表示と実物が一致する
- [ ] ページの読み込みが体感で著しく遅くない（特に宮城県ページ。回線種別を記録する）
- [ ] 戻る操作で元のスクロール位置・開閉状態が大きく崩れない
- [ ] ダークモード / 文字サイズ拡大（iOS のテキストサイズ変更）で崩れない（任意だが記録推奨）

## §2 キーボード操作確認

- **所要時間の目安: 30分**
- **記録先: Issue #12**
- 前提: PC ブラウザ（Chrome 等）で実施。マウスを使わず Tab / Shift+Tab / Enter / Space / 矢印キーのみで操作する。

### 手順と観点（対象: トップ、宮城県、レビュー進捗、訂正・反論）

1. ページを開き、Tab を押していく。
   - [ ] 最初の Tab でスキップリンクが現れ、Enter で本文へ移動できる
   - [ ] フォーカス位置が常に見える（:focus-visible の実表示を確認。静的監査では CSS の存在のみ確認済み）
   - [ ] フォーカスの移動順序が視覚的な読み順と一致する
2. インタラクティブ要素をキーボードだけで操作する。
   - [ ] チップ切替ボタンが Enter / Space で切り替わり、選択状態が支援技術向けにも伝わる作りか（見た目でも判別できるか）
   - [ ] details（カードの開閉）がキーボードで開閉できる
   - [ ] 検索フォーム（宮城県ページ）へ入力し、候補・結果へ到達できる
3. 到達不能な要素、フォーカスが消える箇所、キーボードトラップ（抜け出せない箇所）がないかを通しで確認する。
4. Esc や矢印キーで想定外の挙動をする要素がないか。

## §3 スクリーンリーダー確認（iPhone VoiceOver）

- **所要時間の目安: 45〜60分**
- **記録先: Issue #12**
- 前提: 所有者の iPhone と VoiceOver を使用する。読み上げの「速さ」ではなく「情報が正しく・順序よく伝わるか」を確認するのが目的。

### VoiceOver の開始手順（一般的な iOS の操作）

1. 「設定」→「アクセシビリティ」→「VoiceOver」をオンにする。
2. 操作の基本: 左右スワイプで項目移動、ダブルタップで決定、3本指スワイプでスクロール。
3. 終了時は同じ画面でオフに戻す。サイドボタン等のショートカット（アクセシビリティショートカット）を設定しておくと切り替えが容易（任意）。
   ※ 画面構成・名称は iOS のバージョンで異なる場合がある。実際の表示に合わせて読み替えること。

### 確認観点（対象: トップ、宮城県、レビュー進捗）

- [ ] ページを開いて最初に、ページの目的が分かる見出しが読み上げられる
- [ ] 見出しジャンプ（ローターの「見出し」）で全体構造を把握できる（見出し階層は静的監査で飛びなしを確認済み。実読み上げでの使い勝手が対象）
- [ ] リンク一覧（ローターの「リンク」）で、リンクの目的が判別できる
  - 特にレビュー進捗ページ: 静的所見として「公式資料の索引」という同一テキストのリンクが67件ある。リンク一覧で判別不能であれば要修正として記録する
- [ ] グラフ相当の内容（年度実績の推移）がテキストとして読み上げられ、数値と年度が対応して伝わる
- [ ] 状態ラベル（Reviewed / Partial 等）が記号や色名ではなく言葉で伝わる
- [ ] 宮城県ページ（見出し約195件・リンク約227件）で、目的の情報まで現実的な操作回数で到達できるか（負担が大きければ、その旨を所見として記録する）
- [ ] 読み上げ順序が視覚的な表示順序と矛盾しない
- [ ] 画像の代替テキスト: 静的監査で `<img>` は0件のため対象は限定的だが、アイコン的な要素が無意味な読み上げをしていないか確認する

## §4 Lighthouse accessibility 測定（ローカル Chrome）

- **所要時間の目安: 30分（4ページ分）**
- **記録先: Issue #12（スコアと失敗項目の一覧を貼る）**
- 経緯: 2026-11-15 の監査では、実行環境（CI 相当）の Chromium 制約により Lighthouse を実行できず、スコアは未取得のまま。本節は所有者の PC の Chrome DevTools で実施する手順である。

### 手順（一般的な Chrome DevTools の操作）

1. PC の Chrome で対象 URL を開く（シークレットウィンドウ推奨。拡張機能の影響を避ける）。
2. DevTools を開き、「Lighthouse」パネルを選択する。
3. モードは「ナビゲーション」、デバイスは「モバイル」、カテゴリは **Accessibility**（必要に応じ Best Practices / SEO も同時選択可）を選んで分析を実行する。
4. スコアと、失敗した監査項目（項目名と対象要素）を確認する。レポートは保存（HTML / JSON のエクスポート）しておく。
5. 対象4ページ（トップ、レビュー進捗、宮城県、訂正・反論）で繰り返す。
   ※ DevTools の UI 名称・配置は Chrome のバージョンで異なる場合がある。実際の表示に合わせて読み替えること。

## §5 初見ユーザー 3分理解テスト

- **所要時間の目安: 準備30分＋実施15分／人（被験者 2〜3名を想定）**
- **記録先: Issue #12（被験者ごとの記録様式を集約）**
- 目的: サイトの説明を一切受けていない人が、3分で「何のサイトか」「何が分かり、何がまだ分からないか」「根拠に戻れるか」を把握できるかを確認する。操作の速さのテストではない。

### 実施上の注意

- 被験者には事前にサイトの内容・目的を説明しない。説明してしまった場合はその旨を記録する。
- 被験者の発言は要約ではなく、できるだけ言葉のまま記録する。
- 合否は被験者個人の能力ではなく、サイト側の分かりやすさの評価として扱う。

### 被験者への依頼文案

> 協力のお願いです。自治体の情報をまとめたウェブサイトについて、初めて見た人の感想を聞かせてください。
> スマートフォンでサイトを開いて、3分ほど自由に見てください。そのあと、いくつか質問をします。
> テストされるのはあなたではなく、サイトの分かりやすさです。分からないところがあれば、それ自体が大切な結果なので、遠慮なく言ってください。
> 所要時間は15分ほどです。よろしくお願いします。

### タスク文（読み上げて渡す）

1. サイトを開いて、3分間、自由に見てください（操作の指示はしない）。
2. （3分経過後）タスクA: 「このサイトで、ある自治体について『確認できていること』と『まだ確認できていないこと』の両方が書かれている場所を探してください。」
3. タスクB: 「いま見た情報の根拠（元の公式資料）に戻るには、どこを押しますか。実際にやってみてください。」

### 理解度質問票（3分経過後・タスク後に口頭で質問）

| # | 質問 | 期待する理解（採点用メモ。被験者には見せない） |
|---|---|---|
| Q1 | このサイトは何をするサイトだと思いますか | 自治体の計画・予算・実績などを公式資料に基づいて確認できる、という趣旨 |
| Q2 | このサイトは自治体を採点・ランキングしていると思いますか | していない（点数や順位を出していない）と答えられる |
| Q3 | 表示されている情報のうち、確認済みのものと未確認のものの区別はつきましたか | Reviewed / 未確認範囲の表示に気づいている |
| Q4 | 情報が間違っていたら、どこから知らせることができますか | 訂正・反論の導線（/corrections）にたどり着ける |
| Q5 | もう一度使いたい場面があるとしたら、どんなときですか | 自由回答（想定用途の把握が目的。正解なし） |
| Q6 | 分かりにくかった言葉・場所を挙げてください | 自由回答（用語と画面の改善材料） |

### 記録様式

```
- 被験者: （属性のみ。年齢層・自治体情報への関心度合い。本人を特定する情報は書かない）
- 実施日 / 端末:
- 事前説明の有無: なし / あり（内容）
- タスクA: 到達できた / できなかった（所要時間、迷った場所）
- タスクB: 到達できた / できなかった（所要時間、迷った場所）
- Q1〜Q6 の回答要旨（印象的な発言は原文のまま）
- 観察メモ: （つまずき、誤解、想定外の読み取り）
```

### 合否の目安（サイト側の判定基準案）

次を満たせば「理解テストとして概ね合格」とみなす（**この目安自体、所有者の正式な承認は未取得。実施前に Issue #12 で確定させること**）:

- 被験者の過半数が、Q1 にサイトの趣旨を自分の言葉で答えられる
- 全員が Q2 で「採点・ランキングはしていない」と正しく理解している（誤解した場合は重大な所見として扱う）
- 過半数がタスクA・B の両方に到達できる
- Q3 で確認済み／未確認の区別に過半数が気づいている

基準に届かない項目があった場合は、不合格ではなく「要改善項目」として内容を Issue 化し、文言・導線の修正後に再実施する。
