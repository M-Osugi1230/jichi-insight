# Jichi Insight 障害対応 机上訓練計画（2026-11-15）

- 位置づけ: Public beta ゲート「訂正受付、変更履歴、障害対応、ロールバックを本番相当環境で試験」のうち、**障害対応**を対象とする机上訓練（テーブルトップ演習）の計画書。
- 根拠文書: docs/OPERATIONS_RUNBOOK.md §6（Incident levels）、§7（Rollback）、§9（Monitoring）、§11（公開後4週間の安定運用計測）。
- **本訓練は未実施**（2026-11-15 時点）。本番サイトに障害を再現するものではなく、シナリオに沿って判断と手順を口頭・記録でなぞる訓練である。
- 記録先: 訓練の記録は GitHub Issue [#12](https://github.com/M-Osugi1230/jichi-insight/issues/12) に集約する。訓練で見つけた手順の不備は個別 Issue 化する。

## 先に実施済みのもの（ロールバック訓練）と、本訓練の範囲

### 実地で確認できたこと（ロールバック訓練、2026-11-15 実施済み）

- 無害なテスト変更（訓練用マーカーの追加）を PR #471 でマージし、公開検証（`.github/publication-status.json`）が status=verified かつ deployed_commit_sha がマージコミットと一致することを確認した。
- revert PR #472 をマージし、再デプロイ後に公開検証が再び verified となり、マーカーが main から消えたことを確認した。
- つまり「問題コミットの特定 → revert PR → マージ → 再デプロイ → 公開検証での確認」という §7 の技術的な経路は、本番相当環境で一度完走している。

### 机上でしか確認できないこと（本訓練の対象）

ロールバック訓練は「戻す操作」の確認であり、次の要素は含まれていない。これらは実際に障害が起きてからでは練習できないため、机上で確認する。

- 障害の**検知**: 誰が・どの手段で気づくか（§9 の監視項目を単独運用で実際に回せるか）
- **重大度の判定**: P0 / P1 / P2 の切り分けを、その場の情報だけで行えるか
- **公開停止・ロールバックの判断**: どの条件で「まず止める/戻す」を即断するか、判断の記録をどう残すか
- **連絡経路の実効性**: 訂正受付（GitHub Issues）・非公開事項の扱いが、手順どおりに機能するか
- **時系列記録**: 対応しながら記録を残す運用が破綻しないか
- **対外説明**: 利用者向けに「何が起きて、どこまで分かっていて、いつ更新するか」を書けるか

## 実施体制と進め方

- 参加者: 所有者（大杉邑大）が全ロール兼務（Publication owner / Data reviewer / Engineering owner / Correction owner）のため、進行・判断・記録を一人で担う。**「一人で回すこと自体が成立するか」の確認も本訓練の目的に含む。**
- 所要時間の目安: シナリオ1本あたり 40〜50分（2本で約90分）。1本だけの実施も可。
- 進行方法: 下記の「注入情報（インジェクト）」を時刻順に読み上げ（自分で読み進め）、各時点で「何をするか・何を記録するか」を声に出しながら記録様式に記入する。分からない点・手順書に書いていない点が出たら、それ自体が訓練の成果（不備の発見）として記録する。
- 使用するもの: OPERATIONS_RUNBOOK、CORRECTIONS.md、本計画書、記録様式（本書末尾）。本番環境への変更操作は行わない。

## シナリオA（P1想定）: 主要ページの数値誤表示

### 状況設定

データ品質ページ（/data-quality）の段階サマリで、ある段階の注記が正本データと食い違う数値で表示されていることに、公開後の定期確認で気づいた。サイト自体は表示できており、他のページへの波及は未確認。実際に 2026-11-15 に訂正フローで処理した実在の誤り（Phase 10 段階サマリ注記）と同型の事象を想定する。

### 注入情報と進行表

| 時刻 | 注入情報 | 実施すべき対応（§6 P1 手順に沿う） | 記録するもの |
|---|---|---|---|
| T+0 | 定期確認で誤表示を発見 | 重大度を一次判定（P1 とする根拠を言語化）。Issue を当日中に起票し、公開影響を明記する | 発見時刻、発見手段、対象ページと表示内容 |
| T+10分 | 他ページ（自治体一覧）にも同じ算出表示があると分かる | 影響範囲の洗い出し手順を確認（同じ算出元を使う表示箇所の特定方法） | 影響範囲の一覧、未確認の範囲 |
| T+20分 | 修正にはコード変更と PR が必要で、最短でも数十分かかると判明 | 「修正を待つ」か「該当箇所を一時的に非公開・要確認へ変更する」かの判断（§6 P1 手順2） | 判断と理由、判断者、判断時刻 |
| T+35分 | 修正 PR が用意できた | 通常のレビュー・マージ手順で公開し、Production Smoke と公開検証（verified / deployed SHA）で反映を確認 | マージコミット、確認結果 |
| T+50分 | 本番で正しい表示になったことを確認 | 変更履歴への掲載要否を判断（訂正フローに該当するか）。Issue を完了記録で閉じる | 対応完了時刻、履歴掲載の有無 |

### 判断ポイント

1. P1 と P2 の切り分け: 「重要数値・出典の誤り」は P1（§6）。軽微な表記揺れなら P2。境界の事例を自分の言葉で説明できるか。
2. 一時的な非公開化の判断基準: 誤表示が利用者の判断を誤らせる度合いと、非公開化自体の不利益（情報が消えること）をどう天秤にかけるか。
3. 訂正フローとの接続: この事象は障害対応であると同時にデータ訂正でもある。変更履歴への掲載基準（docs/CORRECTIONS.md）との整合を確認できるか。

## シナリオB（P0想定）: 公開データへの重大な誤り混入

### 状況設定

公開直後の確認で、ある自治体ページに、実在しない数値が「確認済み（Reviewed）」の体裁で表示されていることに気づいた。原因は不明（データ取込の誤りか、表示側の不具合か未判別）。サイトは稼働している。**変形版**: 公開データに個人情報等の機微情報が含まれていた場合の分岐も併せて検討する（その場合は内容を引用・拡散しない対応が先行する）。

### 注入情報と進行表

| 時刻 | 注入情報 | 実施すべき対応（§6 P0 手順に沿う） | 記録するもの |
|---|---|---|---|
| T+0 | 誤った Reviewed 表示を発見 | P0 と一次判定。**公開停止または直前の安全なコミットへのロールバックを先行**させる判断を行う（原因究明より先に止める） | 発見時刻、判定根拠、判断時刻 |
| T+5分 | ロールバック先として「直近の正常な deployment と SHA」を特定する必要がある | §7 手順1 の特定方法を確認（publication-status.json の deployed_commit_sha 等）。訓練では特定手順を口頭で再現する | 特定した SHA とその根拠 |
| T+15分 | ロールバック実施の判断が固まった | 新規マージの停止を宣言する手段を確認（誰に・どう伝わるか。単独運用では「自分が止める」ことの記録方法） | 停止の記録方法 |
| T+25分 | 利用者・関係者への周知が必要と判断 | 連絡経路の確認: サイト上のお知らせ、Issue での公開記録、訂正受付への誘導。非公開にすべき情報（機微情報そのもの）を公開記録に書かない線引き | 周知文の下書き（本書「対外説明の骨子」参照）、公開範囲の判断 |
| T+40分 | 影響範囲の調査が進み、波及は1ページのみと判明 | ロールバック後の復旧手順（原因修正は rollback と分けた PR で行う、§7 手順4）と、再公開の判断条件を確認 | 復旧条件、再公開の判断者 |
| T+55分 | 復旧の見通しが立った | 原因・影響・再発防止を公開可能な範囲で記録する準備（§6 P0 手順5）。Issue #12 への報告要否 | 記録の目次、未確定事項の扱い |

### 判断ポイント

1. **止める判断の速さ**: 原因不明の段階で公開停止/ロールバックに踏み切る基準を、事前に自分の言葉で言えるか。「評価・比較へ反映される大規模な誤データ」は P0（§6）のため、Reviewed の体裁で誤値が出ている場合は原則として先に止める、という運用でよいか。
2. 秘密情報・個人情報が混入した場合の追加対応: 該当情報の失効・再発行（認証情報の場合）、内容を引用しない記録、非表示化・削除の優先（CORRECTIONS.md / Runbook §5 の扱い）。公開 Issue に詳細を書かない線引きを確認する。
3. 連絡経路の実効性: 単独運用で、深夜・外出時に検知できる手段があるか。§9 の監視項目（Actions 失敗、HTTP 応答、公開検証）は「誰が・いつ見るか」が未定義なら、そのこと自体を不備として記録する。
4. 再公開の判断: 誰が何を確認したら再公開してよいか（対象コミット、Smoke、公開検証、影響範囲の確定）を事前に列挙できるか。

### 対外説明の骨子（下書きの型）

```
- 何が起きたか: （対象ページと、誤っていた表示の範囲。機微情報そのものは書かない）
- 現在の状態: （公開停止中 / ロールバック済み / 調査中 のいずれか）
- 利用者への影響: （誤った情報を見た可能性がある期間と範囲）
- 次の更新予定: （いつ、何を報告するか）
- 問い合わせ・訂正の窓口: （GitHub Issues への誘導）
```

## 実施後の処理

1. 記録を Issue #12 に投稿する。
2. 発見した不備は個別 Issue 化し、Runbook 等の改訂は通常の PR 手順で行う。
3. RELEASE_CHECKLIST の該当項目（Final gates の「障害対応…を本番相当環境で試験」）の扱いは、机上訓練の証跡をもって公開責任者が判断する。**机上訓練は本番相当環境での実地試験とは同一ではない**ため、その区別を記録に明記すること。
