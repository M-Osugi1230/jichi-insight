## 1. 現状

- Muse の GitHub App には **workflows 権限がない**。このため、ワークフローファイル（`.github/workflows/*.yml`）を変更する PR は、Muse 経路ではブランチ更新（base の取り込み）が 403 で失敗し、更新・マージができない。読み取りと、ワークフローを含まない PR の操作は可能。
- 実測の経緯: 滞留 PR の棚卸し時に PR #14 でブランチ更新を試み、403 となったことで確定した制約。以後の調査で同種の PR が計5件あることを確認している。
- この制約は「ワークフローの変更ができない」ことであり、サイト本体・データ・文書の作業には影響していない。ただし下記 §2 のセキュリティ・運用上の改善が、この制約のために未適用のまま滞留している。

## 2. 未適用のまま滞留している準備済み作業

### (1) ワークフロー最小権限パッチ（セキュリティ所見 F1 への対応）

- 内容: `workflow-least-privilege.patch` に保存済み。2ファイル・各1行の変更。
  - `build-phase10-core-linkage.yml`: `permissions: contents: write` → `read`
  - `discover-phase10-accountability-sources.yml`: `permissions: contents: write` → `read`
- 根拠: 両ワークフローは `pull_request` トリガーを持ちながら `contents: write` を宣言している。成果物のアップロード（upload-artifact）は contents: write を必要としないため、最小権限の観点で read へ下げられる可能性が高い（security-audit F1）。同一リポジトリのブランチ PR では write トークンでコードが実行される点がリスク。
- 注意: 「書き込みを要する工程が実行時に存在しないか」は実行履歴での裏付けが未実施。適用後は両ワークフローの実行結果を確認すること。
- 適用にはワークフローファイルの変更が必要なため、本件の権限問題と一体で滞留している。

### (2) CI の frozen-lockfile 化（セキュリティ所見 F2 の残件）

- 経緯: F2（lockfile 不在）は PR #460 で `pnpm-lock.yaml` をコミットし前半が解消済み。
- 残件: CI の `pages.yml` / `quality.yml` は install 時に `--no-frozen-lockfile` を明示指定しているため、lockfile があっても CI の依存解決は固定されない。frozen 化（フラグの除去/変更）にはワークフローファイルの変更が必要で、未実施。
- 影響: 現状でもビルドは動作しているが、CI 実行ごとの依存解決の再現性は保証されない。

## 3. 選択肢

### 選択肢A: Muse の GitHub App へ workflows 権限を追加する

一般的な流れ（GitHub App の権限変更は、App の設定変更と、インストール先アカウントでの承認の両方が必要な仕組みである。**具体的な画面構成・手順の詳細は未確認**であり、実施時は GitHub の公式ドキュメントと実際の画面で確認すること）:

1. App の管理画面で、リポジトリ権限に workflows（Workflows）の追加を申請・設定する。
2. インストール先（アカウント M-Osugi1230）側で、権限変更の承認を行う。
3. 承認後、Muse 経路で対象 PR のブランチ更新・マージ、最小権限パッチの適用 PR、frozen 化 PR が実施可能になる。

影響範囲:

- 以後、ワークフローを変更する PR・パッチを Muse が通常の承認フロー（PR 作成→所有者のマージ承認）の範囲で処理できる。滞留5件と未適用2件をまとめて解消できる。
- workflows 権限は CI/CD 定義そのものを変更できる強い権限であり、App に恒常的に付与される。マージには引き続き所有者の承認が介在するが、「変更案を作れる範囲」は広がる。
- ADE の自動マージゲート（ade-remote-pr-gate）等、他の自動化との兼ね合いは本権限とは別に管理される（security-audit F5 は別途、ADE 再開判断時に再確認）。

### 選択肢B: 所有者が GitHub 画面で該当 PR を直接処理する

一般的な流れ（画面仕様の詳細は未確認。実際の表示に合わせて操作すること）:

1. 対象 PR を1件ずつ開き、変更内容（ワークフローの差分）を確認してマージする。ブランチが古く競合する場合は、画面上の更新操作またはローカルでの解決を行う。
2. 適用順序の目安（棚卸し資料の推奨）: 影響の小さいものから1件ずつ、公開検証を挟んで進める。例: #14（quality.yml の1行）→ #13（部分適用か一括かの判断とセット）→ デプロイ経路の #28 → #29 → #15。
3. 最小権限パッチと frozen 化は、所有者がブランチを作成して PR 化するか、Muse がワークフロー以外の形で下書きを用意し、所有者がワークフロー差分を反映する。
4. 各マージ後に `.github/publication-status.json` の verified 更新で本番への影響がないことを確認する。

影響範囲:

- App の権限は現状のまま（拡大しない）。セキュリティ上の恒常的な変更は生じない。
- 所有者の手作業が都度発生する。対象は当面7件（PR 5件＋パッチ適用＋frozen 化）で、将来もワークフロー変更のたびに同様の手作業が要る。
- 特にデプロイ経路（pages.yml）を含む変更は、1件ずつの適用と公開検証の確認が推奨されており、画面操作でもその手間は変わらない。

## 4. 比較と推奨

| 観点 | A: App へ権限追加 | B: 所有者が画面で処理 |
|---|---|---|
| 滞留の解消 | 5件＋未適用2件を Muse 経路で処理可能 | すべて所有者の手作業で処理可能 |
| 権限の変化 | workflows 権限が恒常的に追加される（強い権限） | 変化なし |
| 今後の運用 | ワークフロー保守を Muse に任せられる | ワークフロー変更のたびに所有者作業が発生 |
| 手間 | 初回の権限変更手続きのみ | 1件ごとの確認・マージ操作が継続 |
| リスク | App の権限範囲の拡大。承認フローは維持される | 操作ミスは画面操作でも起こりうるが、範囲は都度限定的 |

推奨の考え方（中立な整理）:

- ワークフロー変更は頻度が低い作業であり、現在の滞留は一過性の解消で足りるなら、権限を広げない **B が無難**。
- 今後、依存更新や CI 改善を継続的に Muse へ任せたいなら、**A が運用に合う**。その場合は、権限追加の際に App の他の権限範囲も併せて棚卸しすることを勧める。
- どちらを選んでも、最小権限パッチと frozen 化の「適用後にワークフロー実行結果と公開検証を確認する」工程は省略できない。
- 混在する論点として、#13 の checkout は「5ファイルの部分適用か、全ワークフロー一括更新か」という適用範囲の判断が別に残る。これは A/B どちらの経路でも先に決める必要がある。
