- 本報告書は棚卸しのみ。コード変更・PR は行っていない。

## 結論（要点）

1. **スキーマは揃っているが、事業レコードの実データは 0 件。** project / kpi / promise / contract の各スキーマと example は存在するが、data/ 内にこれらをインスタンス化した reviewed レコードは存在しない（後述の検出スクリプトで全件確認済み）。#7 は「スキーマ設計から」ではなく「既存スキーマへの実データ登録から」始められる。
2. **最も進んでいる資産は福岡県の Phase 10 接続台帳。** 県の行政評価（事務事業評価）266 事業について、事業名・担当課・事業費・目的・内容・成果指標テキスト・評価方向性を抽出済みで、予算・決算・総合計画目標への照合候補も付いている。ただし状態は `candidate_review` で、目標との完全一致確定は 1 件のみ（partial 108 / not_linked 157）。Reviewed への昇格作業が #7 の中心になる。
3. **3自治体とも、事業単位の公式資料は存在する。** 特に北九州市の行政評価（事業評価）は、1 資料の中に KPI（基準値・目標値・実績値・達成率）・当初予算額・決算額・評価・翌年度の方向性まで揃い、ライフサイクルの核として最も扱いやすい。福岡県は行政評価レポートが同等の役割を果たす。福岡市は資料が分散しており（予算＝当初予算案等説明資料、決算＝決算説明資料、KPI 実績＝施策評価）、事業単位でつなぐ接続作業が最も重い。
4. **公式の「重点」母集団は県と北九州市にはある。福岡市には単一の公式リストがない**（後述）。選定基準は自治体ごとに公式母集団を定義し、機械的な抽出ルールで決める設計が必要。

## 3. 不足点の整理

1. **福岡市の母集団定義**: 単一の公式「重点事業」リストがない。重要施策（予算資料）と施策評価の事業の 2 系統から母集団を定義する規約が必要で、県・北九州市より選定基準の説明が一段重くなる。
2. **福岡市の KPI と金額の分離**: KPI 実績は施策評価、金額は予算・決算説明資料と別資料にあり、事業名の表記ゆれを吸収する同一性確認が手作業になる（県の linkage 台帳で partial が 108 件残ったのと同じ課題）。
3. **県の目標↔事業接続**: 総合計画 118 目標と 266 事業の個票接続は候補段階（完全一致 1 件）。「関連する計画」欄は、計画体系の位置（柱・中項目・小項目・具体的取組）が評価書に印字されているため**体系経由の接続は可能**だが、目標（KPI）単位の接続は個別確認が必要。
4. **指標の構造化**: 県の評価書の成果指標はテキスト形式（目標・実績が文章・表内に混在）。kpi.schema の observation 構造へ落とす抽出・検証作業が事業ごとに発生する。北九州市は表形式で構造化しやすい。福岡市施策評価も表形式だが年度系列は最新値中心。
5. **段階の表記ゆれ**: 県評価書の翌年度事業費は「予算案の額」、北九州市の決算額は認定前の可能性など、**資料の値がどの段階のものか**を資料ごとに固定してから登録する必要がある（#6 で両市予算の「案→成立」差し替えを行ったのと同じ論点）。
6. **契約・議会・監査の事業単位接続**: 3自治体とも公表自体はあるが、事業との対応付けの公式な対応表はない。受け入れ条件でも「公式に入手可能な場合」と限定されているため、30 件全件に必須とせず、確認できた事業のみ登録し、未確認は未確認と明示する設計が現実的。
7. **首長公約との接続**: promise レコード自体が未登録（Issue #8 の領域）。#7 では related_promise_ids を空のまま許容し、#8 側で接続する順序が妥当。

## 4. 進め方の設計案

### 4.1 事業の選定基準（公式母集団＋機械的ルール）

- 母集団は自治体の公式リストに限定する:
  - 福岡県: 行政評価の事務事業評価 266 事業（＋新規は政策事前評価）
  - 北九州市: 新ビジョン主要事務事業 198 事業
  - 福岡市: 当初予算案等説明資料「重要施策」の事業 ∩ 施策評価で指標を持つ事業（両方に載るものを優先し、片方のみの場合は理由を記録）
- 母集団からの抽出は再現可能なルールで行う: **計画体系の柱（県: 総合計画の柱／北九州市: 3つの「まちの姿」と重点戦略／福岡市: 基本計画の目標）ごとに、公式資料の掲載順に先頭から選ぶ**層化抽出とし、分野の偏りを避ける。金額の大小で選ばない（大きな事業だけが「重点」に見える歪みを避ける）。
- 選定した 30 件と抽出ルールをカタログに記録し、選定自体を reviewed の対象にする。

### 4.2 30件の配分案

- **3 自治体 × 10 件**（県・政令市・中核市等という受け入れ条件の「3つの自治体種別」に対応する構成として、県 1・政令市 2 で 10 件ずつ均等配分）。
- 各自治体内では計画体系の柱ごとに 2–3 件ずつ層化し、継続事業を中心に、完了・廃止事業を各自治体 1 件まで含める（ライフサイクルの「翌年度の扱い」が完了の場合も表示できるようにするため）。

### 4.3 データモデルの叩き台

既存スキーマを核とし、新規設計は最小限にする。

- **事業系列と年度レコードの 2 層**: project.schema は fiscal_year を必須とする単年度レコードなので、同一事業の複数年度は「同一の事業系列 ID を共有する年度別 project レコード」として登録し、系列の同一性は担当課・計画体系位置・事業名の継続性で確認する（千葉の versioned_project_linkage の前例を汎用化）。系列をまたぐ変更（改称・組み替え・分割）は change note を必須とする。
- **予算段階**: budget_records の kind（initial_budget / revised_budget / execution / settlement）をそのまま使う。補正は回次を note に必須記載（例:「令和7年度2月補正」）とし、値が「案」段階のものは note にその旨を明記して成立後の値と混ぜない。execution（執行額）は公式に事業単位で得られる自治体が限られるため、空を許容し「未公表」と明示する。
- **KPI**: kpi.schema の observation 構造（baseline / target / actuals を別フィールドで保持）をそのまま使い、target の版（当初目標か改訂目標か）は annual_actual_linkage の target_version_status の前例に倣って note / status で区別する。causality_note は原則必須運用とし、「この指標の変動が事業の成果であるとは限らない」旨の定型＋事業固有の事情を書く。
- **評価・監査・議会**: 公式資料に載る評価（県の方向性、北九州市の評価区分、福岡市の施策評価）は「公式の評価」として出典付きで登録し、Jichi 独自の評価は作らない（政治的中立性・採点しない原則）。事実／解釈／評価の層分離は、レコード上は出典パケットと note の分離、表示上は既存の EvidencePanel / boundary 表現を踏襲する。
- **出典パケット**: 事業ごとに evidence_packet を必須とし、資料名・公表主体・対象年度・ページ位置を記録する（受け入れ条件「全事業に公式の出典パケット」）。

### 4.4 パイロットの進め方

1. **北九州市 3 件で先行**（資料が単一で完結し、project/kpi スキーマへの登録と検証フローを最小コストで確立できる）。うち 1 件は決算額の認定後確定値との突合サンプルを兼ねる。
2. **福岡県 3 件**（linkage 台帳の partial 候補から、担当課・計画体系で同一性が確認できるものを昇格させる手順を確立）。
3. **福岡市 3 件**（予算資料×施策評価の 2 資料接続の手順を確立）。
4. パイロット 9 件で登録規約（段階の扱い・補正の回次・KPI の版・系列 ID）を固定し、残り 21 件を同規約で展開。描画 UI はデータ確定後に仕様を GPT 側へ引き渡す（#6 と同じ分担）。

## 5. 受け入れ条件との対応

| 受け入れ条件 | 現状 | 見通し |
|---|---|---|
| 重点事業が最低30件 Reviewed | 0 件（候補は県 266 件分あり） | 母集団と抽出ルールを決めれば到達可能 |
| 全事業に公式の出典パケット | パケットの仕組みは既存 | 登録時の必須運用で対応 |
| 予算の段階と年度が明示 | project.schema の budget_records が対応 | 補正の回次と「案」段階の扱いの規約決めが必要 |
| KPI の目標値と実績値を混同しない | kpi.schema が構造で分離済み | 県のテキスト指標の抽出検証が作業の中心 |
| 因果関係の限界が表示される | causality_note フィールドあり | 必須運用＋表示は UI 仕様に含める |
| 3つの自治体種別で再利用可能 | スキーマは自治体汎用 | 県・政令市 2 市のパイロットで検証する |
| 事業ごとの詳細項目（目的・対象、計画・公約、契約、議会・監査、翌年度の扱い、層分離） | スキーマに受け皿あり（target_population / related_promise_ids / contract.project_id 等） | 契約・議会・監査は「入手可能な場合」の範囲で登録。公約は #8 と連携 |
