## 2. リポジトリ側の既存資産

### 2.1 promise スキーマ（`schemas/promise.schema.json`）

個別公約レコードの正本スキーマ。主要フィールドは Issue #8 のスコープをほぼ網羅している。

| 観点 | フィールド | 内容 |
|---|---|---|
| 同定 | `id` | パターン `^[a-z0-9-]+-promise-[0-9]{3,}$`（例: `jp-local-401005-executive-2023-02-20-promise-001` 形式が example の流儀） |
| 所属 | `municipality_id` / `executive_term_id` | 自治体コード（`jp-local-XXXXXX`）と任期 ID への参照 |
| 原文 | `original_text` / `source_location` | 原文の短い抜粋と、第三者が照合できる資料位置 |
| 要約 | `plain_summary` | 平易な要約（任意、null 可） |
| 種別 | `statement_type` | `specific_commitment` / `directional_commitment` / `vision` / `supporting_context` の4区分 |
| 分野 | `policy_area` | 自由文字列 |
| 質の次元 | `baseline` / `target` / `deadline` / `funding_statement` / `controllability` / `assessability` | 基準値・目標・期限（date）・財源の言及・制御可能性（high/medium/low/shared/not_assessable）・評価可能性（assessable/partially_assessable/not_assessable）。いずれも「資料に明示がある場合のみ記録」がルール |
| 進捗 | `progress_state` | `achieved` / `mostly_achieved` / `partially_achieved` / `in_progress` / `not_started` / `changed` / `abandoned` / `not_assessable` の8値 |
| 変更 | `change_explanation` | 変更・遅延・撤回への公式説明を入れる欄（任意） |
| 接続 | `related_project_ids` | 事業 ID の配列 |
| 品質 | `review_status` / `confidence` / `sources` | verified/reviewed/extracted/inferred/missing、high/medium/low/not_assessable、出典カタログ ID（1件以上必須） |
| 抽出 | `extraction_note` | 分割判断のメモ |

スキーマレベルの安全不変条件（`allOf`）:
- `statement_type` が `vision` / `supporting_context` の場合、`assessability` と `progress_state` は `not_assessable` でなければならない。
- `assessability = not_assessable` の場合、`progress_state` は `not_assessable` でなければならない（未評価を「未着手」に変換しない）。

テストは `tests/test_promise_contract.py`（example の検証、上記不変条件の検証、出典 ID として `kitakyushu-mayor-election-2023-bulletin` が使えることの検証）。

### 2.2 周辺スキーマ

- **`executive_term.schema.json`**: 任期メタデータ。`office`（governor/mayor）、`person_name`、`term_start`、`term_end`（null 可）、`election_date`、`status`（current/completed/resigned/vacant）、`manifesto_source_ids`（公約資料の出典 ID 配列）を持つ。ID は `jp-local-XXXXXX-executive-YYYY-MM-DD` 形式。
- **`manifesto_review.schema.json`**: 資料から個別公約を作る前の人手レビュー判断。`review_scope`（document/candidate_panel/section）、`statement_boundary`（clear/mixed/unclear）、`segmentation_status`（segmented/manual_review_required/not_segmented）、`promise_records_created`、`reason_codes`（mixed_narrative / biography_and_policy_combined / no_explicit_list / low_legibility / source_incomplete / other）。**安全不変条件: `manual_review_required` または `not_segmented` の場合 `promise_records_created` は 0 でなければならない**（`schemas/MANIFESTO_REVIEW.md` に契約の説明あり）。
- **`manifesto_source_search.schema.json`**: 原文資料を特定できない場合の探索記録。`result_status` は `source_registered` / `official_result_only` / `no_stable_primary_source_found` / `follow_up_required` の4値で、`nonexistence_claim`（資料が存在しないという主張をしないことの明示）が必須項目。
- **`source_request.schema.json`**（運用は `docs/SOURCE_REQUESTS.md`）: 行政機関への照会案の管理。draft は未送信であり、送信したことにはならない、という状態分離が明文化されている。

## 5. 進め方の設計案

### (a) 母集団の定義

- 原則は「**任期ごとに、公約文書そのものを母集団とし、その全項目を登録対象とする**」。文書が複数ある場合は `docs/PROMISE_EXTRACTION.md` の優先順位（選挙公報 ＞ 候補者公式マニフェスト）で主文書を1つ定め、他方は補足出典として同じ項目の `sources` に併記し、同一公約の重複登録を避ける。
- 数え方の単位は、資料上の境界（見出し・箇条書き・番号項目）を1単位とする既存の分割ルールをそのまま使う。柱（大項目）と小項目の階層がある文書（福岡市の6本柱、北九州市の7つの基本政策）では、**小項目を promise レコードの単位**とし、柱は `policy_area` とグルーピング（必要なら柱自体を `vision` / `directional_commitment` のレコードとして別途保持）で表す案が、進捗を追える粒度として適切。
- 文章型で分割できない資料（北九州市の選挙公報）は、manifesto_review の `manual_review_required` を維持して無理に分割せず、主文書を候補者公式マニフェスト側に置く。選挙公報は「選挙時に候補者が公表した方向性」の出典として任期側に紐付けて保持する。
- `statement_type = supporting_context`（経歴・決意・実績説明）にあたる部分は公約レコードを作らず、その判断を manifesto_review の `reason_codes` と `review_note` に残す。これにより受け入れ条件「特定した公約はすべて記録するか、記録できない理由を明示する」を、promise レコード群＋分割レビュー記録の組み合わせで満たす。
- アーカイブ（web.archive.org 等）にのみ現存する公式文書の扱い: 発行主体が公式（選管・候補者本人）である文書の保存コピーについては、原本 URL・発行主体・アーカイブ取得日時を出典カタログの `notes` に明記したうえで登録可能とする案を推す。ただしこれは出典ポリシーの判断事項であり、実装前にプロジェクト側で確定させる必要がある。

### (b) 進捗状態の語彙

- 正本は promise スキーマの `progress_state` 8値とする。新規の語彙は作らない。
- 初期値は全件 `not_assessable` とし、実行資料・予算・事業・KPI・公式説明への接続ができた項目から順に状態を付ける（既存ルール: 選挙資料の事実だけで `not_started` と判定しない）。
- 自治体公式の進捗区分がある場合は、その区分を原文のまま併記し（事業データの `official_evaluation` と同じ考え方）、スキーマ値への変換表を自治体ごとに固定して証拠パケットに残す。現3首長では公約特化の公式区分は未確認のため当面は証拠ベース判定が主になるが、北九州市の前市長方式（「達成」→ achieved、「推進中」→ in_progress）が変換表の前例になる。
- `changed` は失敗カテゴリではなく独立の状態として扱い、必ず `change_explanation`（公式説明の出典つき）とセットで使う。`abandoned` も公式な撤回・終了の表明がある場合に限る。

### (c) 公約の質の次元の記録方法

- 既存フィールドで「事実として」記録し、採点には変換しない。
  - 具体性: `statement_type`（specific / directional / vision / supporting_context の4区分）
  - 目標・期限・財源: `baseline` / `target` / `deadline` / `funding_statement`。**原文に明示がない場合は null とし、「原文に記載がない」という事実そのものを表示する**。任期満了日を期限として補完しない。
  - 制御可能性: `controllability`（自治体単独で実行可能か、国・県・議会・民間との共同が必要か。不明は `not_assessable`）
  - 評価可能性: `assessability`（対象・行為・根拠の有無）
- 表示側では次元ごとの事実（例: 「数値目標あり／期限の記載なし／財源の言及あり」）を並べるにとどめ、合計スコア・星・順位などの総合評価には変換しない。首長の総合スコアを公開しないという受け入れ条件と一体で運用する。
